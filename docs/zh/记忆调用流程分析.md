## 1. 记忆体系全景

JiuwenSwarm 的"记忆"并非单一组件，而是 **7 个相互独立、各自有触发时机与生命周期的子系统**，按写入/读取时机可分为三大类：

| 类别 | 子系统 | 写入/触发方式 | 写入本地/外接 | 涉及 agent 模式 | 适用模式（原文） |
|------|--------|--------------|--------------|----------------|------------------|
| **会话内即时写入** | ① 内置记忆索引（`write_memory`/`read_memory`/`memory_search`） | Agent 主动调用工具 | **本地**（`memory/*.md` + `memory.db`） | `agent.fast`/`agent.plan` | Agent 模式 |
| 会话内即时写入 | ④ 编码记忆（`coding_memory_read/write/edit`） | Agent 主动调用工具 + Rail 主动召回 | **本地**（`coding_memory/<project>/*.md` + `memory.db`） | `code.*` | Code 模式 |
| 会话内即时写入 | ⑥ 项目记忆（`JIUWENSWARM.md`） | 用户手写文件，Rail 每轮注入提示词 | **本地**（项目内 `JIUWENSWARM.md`，不进索引） | `code.*` | Code 模式 |
| **对话后自动提取** | ③ 自动记忆（Auto Memory） | 对话结束触发后台子代理提取 | **本地**（写 `coding_memory/<project>/*.md`，复用编码记忆存储） | 全模式可触发（需 `auto_memory_enabled` + `modes.<mode>.memory.enabled`，默认 config 两模式都 true）；⚠️ agent 模式触发后写入但无 CodingMemoryRail 检索，实际"写了用不上"（§4.10） | 全模式（需开关） |
| **睡时离线整理** | ② Dreaming | 定时后台扫描历史会话，LLM 提取后写入 | **本地**（agent→`memory/DREAMING.md`；code→`coding_memory/consolidated_*.md`，⚠️ 不被索引见 §3.6）；**不碰外接**（§3.1） | `agent.fast`/`agent.plan`（agent 模式）/ `code.*`（code 模式） | Agent / Code 模式 |
| **Provider 接入** | ⑤ 外接记忆（Mem0/OpenViking/openjiuwen LTM/BlinkMem） | 由 provider 决定（`sync_turn` 每轮回写 + `handle_tool_call` 工具） | **外接**（provider 自管存储，不进本地索引） | 仅 `agent.fast`/`agent.plan`（code 模式不挂外接，见 §1 模式矩阵） | Agent plan/fast 模式 |
| **任务级经验** | ⑦ 经验记忆（`experience_*`） | Agent 主动调用工具 | **本地**（`task-data.json`）+ context_evolver 服务端；**不调外接**（走 `openjiuwen.extensions.context_evolver` 扩展，与 `MemoryProvider`/`ExternalMemoryRail` 平行，互不感知） | ⚠️ **代码已实现但未注册**（见第 8 节），实际无模式涉及 | ⚠️ **代码已实现但未注册**（见第 8 节） |

### Agent 模式体系（理解各模式记忆行为的前提）

JiuwenSwarm 的模式是**两级结构**，在 `config.yaml:927` 的 `modes:` 段定义，由 `_adapter_mode_for_request`（`interface.py:602-612`）和 `create_adapter`（`agent_adapters.py:116-137`）分派到不同适配器。**不同模式的记忆子系统组合不同**，这是理解后续触发时机的前提。

#### 一级模式（3 种，对应 3 个适配器）

| 一级模式 | 适配器 | 用途 | 记忆系统 |
|---------|--------|------|---------|
| **`agent`** | `JiuWenSwarmDeepAdapter` | 通用对话/规划智能体 | 内置 MemoryRail + 外接 ExternalMemoryRail（均可挂） |
| **`code`** | `JiuWenSwarmCodeAdapter` | 代码任务（读写文件/LSP/代码记忆） | CodingMemoryRail + ProjectMemoryRail（内置，不受 `memory.engine` 管） |
| **`team`** | team 适配器 | 多智能体协作 | 团队共享记忆 `TEAM_MEMORY.md` + 成员各自记忆 |

#### 二级子模式

**`agent` 下两个子模式**（`config.yaml:931-942`）：

| 子模式 | 全称 | 特点 | memory 默认 | is_proactive |
|--------|------|------|------------|-------------|
| **`fast`** | `agent.fast` | 性能模式（默认） | `enabled: true` | `false`（被动，用户问才搜） |
| **`plan`** | `agent.plan` | 规划模式（深度） | `enabled: true` | `true`（主动，每轮自动搜+记） |

**`code` 下子模式**（`code.normal` / `code.plan`）：`_resolve_mode_memory`（`config.py:209-210`）对 `code.*` **忽略 sub_mode**，都映射到 `modes.code`。即 code 的子模式在记忆配置上无差异，均用 `modes.code.memory.enabled`（默认 true）。

**`team`** 下有 `jiuwen_team`（`config.yaml:980`），含 leader/agents/workspace/transport/storage/team 级共享记忆。

#### 模式分派逻辑（代码坐实）

`_adapter_mode_for_request`（`interface.py:602-612`）把请求的 `mode` 参数归一：
```python
if mode == "team.plan": return "code"          # team.plan 实际走 code 适配器
if mode == "code" or mode.startswith("code."): return "code"
return "agent"                                  # 其余（含 fast/plan/agent.*）走 deep
```

`create_adapter`（`agent_adapters.py:133-137`）：
```python
if mode == "code": return JiuWenSwarmCodeAdapter()
return JiuWenSwarmDeepAdapter()                 # agent/team 都走 deep
```

模式格式约定（`_resolve_mode_memory`，`config.py:193-228`）：
- `agent.plan` / `agent.fast` / 裸 `plan` / `fast` → `modes.agent.{plan|fast}`
- `code` / `code.normal` / `code.plan` → `modes.code`（忽略 sub_mode）
- `team.plan` → 经 `_adapter_mode_for_request` 转成 `code`

#### 各模式记忆系统挂载矩阵

| 模式 | 内置 MemoryRail | CodingMemoryRail | ProjectMemoryRail | 外接 ExternalMemoryRail |
|------|----------------|------------------|-------------------|------------------------|
| `agent.fast` | 受 `memory.engine` + `modes.agent.fast.memory.enabled` 门控 | ❌ 不挂（code 专属） | ❌ 不挂（code 专属） | ✅ 可挂（`engine∈{external,both}`） |
| `agent.plan` | 受 `memory.engine` + `modes.agent.plan.memory.enabled` 门控 | ❌ 不挂 | ❌ 不挂 | ✅ 可挂 |
| `code.*` | ❌ 不支持（code 用 CodingMemoryRail 替代，`interface_code.py:597-601`） | ✅ 挂（`modes.code.memory.enabled`，默认 true） | ✅ 挂（同开关） | ❌ **不挂**（code `_update_rails_for_mode` 不调外接 handler） |
| `team` 成员 | 成员各自按 agent 模式 | — | — | 取决于成员模式；另有团队共享 `TEAM_MEMORY.md` |

**关键约束**：
- **外接记忆只在 `agent.fast`/`agent.plan` 模式生效**——`_handle_external_memory_rail_by_config` 只在 DeepAdapter 的 `_update_plan_mode_rails`/`_update_agent_mode_rails` 里调（`interface_deep.py:3855,3946`）；code 适配器覆写 `_update_rails_for_mode`（`interface_code.py:1019`）不调此 handler。
- **`code` 模式的"内置"是 CodingMemoryRail，不是 MemoryRail**——不受 `memory.engine` 控制，由 `modes.code.memory.enabled` 独立门控。故"关闭内置只用外接"在 code 模式不可行。
- **`memory.engine` 的 `external`/`both`/`none` 只影响 agent 模式的 MemoryRail + 外接 Rail**，对 code 的 CodingMemoryRail/ProjectMemoryRail 无影响。

### 2.1 定位

### 2.5 SQLite/FTS5/向量索引的构建与更新

**存储路径**：`_resolve_db_path()`（`manager.py:151`）→ `<workspace_dir>/memory/memory.db`，与 `MEMORY.md` 同目录。连接参数 `journal_mode=WAL`、`check_same_thread=False`、`row_factory=Row`（`manager.py:172-181`）。

**Schema**（`_ensure_schema`，`manager.py:183`）：

| 表 | 行号 | 用途 |
|----|------|------|
| `meta` | `:188` | 键值；`META_KEY="memory_index_meta_v1"` 存 provider/model/chunkTokens，变更触发全量重建（`_should_full_reindex`，`:495`） |
| `files` | `:200` | 每文件 source/hash/mtime/size — 驱动增量同步 |
| `chunks` | `:218` | id/path/source/start_line/end_line/hash/model/text/**embedding BLOB**/updated_at；id = `"{path}:{startLine}:{endLine}"`（`:677`） |
| `embedding_cache` | `:246` | (provider+model+provider_key+hash) → embedding BLOB+dims，避免重复 embed |
| `chunks_fts` | `:261` | contentless FTS5（`content=''`，`contentless_delete=1`），仅 `fts.enabled` 时创建 |
| `chunks_vec` | `:325` | `vec0(embedding float[{dims}])`，懒创建于 `_ensure_vector_table`（`:309`），dims 变更则 drop+recreate |

向量 BLOB 编解码用 `struct.pack(f'{n}f', *v)` / `struct.unpack`（`manager.py:45-53`）。

**初始化序列**（`_initialize`，`manager.py:129`）：
1. 捕获运行中的 event loop（`:132`）
2. 解析 DB 路径、开连接、`_ensure_schema()`
3. `_initialize_provider()` → `create_embedding_provider`（`embeddings.py:137`）：有 embed API key（env `EMBED_KEY`/`EMBED_API_KEY` 或 config `embed.embed_api_key`）用 `OpenAICompatibleEmbeddingProvider`，否则降级 `MockEmbeddingProvider`（128 维 MD5 种子随机）。`provider_key = f"{provider.id}:{provider.model}"`（`:286`）
4. `_load_vector_extension()`（`:292`）：`import sqlite_vec` → `sqlite_vec.load(self.db)`；失败非致命（降级内存 cosine）
5. `await self.sync(reason="initial")`
6. 若 `sync.watch`（默认 True）→ `_setup_file_watcher()`
7. `_ensure_interval_sync()`

**同步流水线**（`sync`，`manager.py:470`）：

```
sync(reason, force)
 ├─ _should_full_reindex()          # meta 缺失 OR provider/model/chunkTokens 变更
 │    └─ true → _run_reindex() → 写 META_KEY，return
 ├─ if "memory" in sources and self.dirty: _sync_memory_files(); self.dirty=False
 └─ if "sessions" in sources:                _sync_session_files()
```

- `_sync_memory_files`（`:574`）：`list_memory_files`（`internal.py:30`，扫 `MEMORY.md`/`memory.md` + `workspace/memory/**/*.md` + `extraPaths`），逐文件 hash（`build_file_entry`），**仅当内容 hash 变化才重建索引**（`:596`）。删除文件则剪枝（`:601-604` → `_remove_file_from_index`）
- `_sync_session_files`（`:606`）：遍历 `workspace/sessions/**/*.jsonl`，同样 hash-diff，source 标记 `"sessions"`
- `_index_file`（`:641`）：读文件 → `chunk_markdown` → 删该 path 旧 chunks/FTS 行 → 逐 chunk `_index_chunk`
- `_index_chunk`（`:670`）：embed（带缓存查表）→ `INSERT OR REPLACE INTO chunks ... RETURNING rowid` → 写 `chunks_fts`（按 rowid）→ 写 `chunks_vec`（`vec_f32(?)`，`:711`）
- `_remove_file_from_index`（`:715`）：从 vec + FTS 删 rowid，再从 `chunks` 和 `files` 删

**分块**（`chunk_markdown`，`internal.py:81`）：行感知、token 预算：目标 `chunking.tokens`（默认 256）+ `chunking.overlap`（默认 32）。token 数用 `len(text)//4` 估算（`estimate_tokens`）。

**Embedding 缓存**（`_get_embedding`，`manager.py:744`）：SHA-256 hash 查 `embedding_cache`，键 `(provider, model, provider_key, text_hash)`；miss 则调 `provider.embed_query` 并回写。模型切换后即使文本未变也会重新 embed。

**文件监控**（`_setup_file_watcher`，`manager.py:339`）：
- 用 **watchdog** `Observer`，监控 `MEMORY.md`/`memory.md`、`workspace/memory/`（递归）、各 `settings.extraPaths`（`:366-380`）
- `MemoryFileHandler`（内部类，`:345`）对 modified/created/deleted 调 `_schedule_watch_sync(path, event_type)`
- **1 秒武装延迟**（`call_later(1.0, _set_watcher_initialized)`，`:402`）防止启动扫描期间的初始事件洪流触发误同步
- `_schedule_watch_sync`（`:416`）线程安全（`call_soon_threadsafe`），按 `sync.watchDebounceMs`（默认 2000ms）去抖，重排 pending 定时器

**定时同步**（`_ensure_interval_sync`，`manager.py:449`）：若 `sync.intervalMinutes > 0` 则起长任务 `interval_sync`，睡 `minutes*60` 后 `sync(reason="interval")`。默认配置 `intervalMinutes: 0`（关闭）——watchdog 是主触发器。

### 2.6 混合检索流水线

入口：`search(query, opts)`（`manager.py:781`）

```
search(query, opts)
 1. if sync.onSearch(默认True) and self.dirty → await sync(reason="search")   (:793)
 2. opts: minScore(默认0.7)、maxResults(默认10)、
         hybrid{enabled, vectorWeight 0.7, textWeight 0.3, candidateMultiplier 2.0}
 3. candidates = min(200, max(1, maxResults * candidateMultiplier))           (:808)
 4. keyword_results = _search_keyword(query, candidates)   if hybrid & fts_available
 5. query_vec = _embed_query_with_timeout(query)   # 60s 硬超时 (:1070)
 6. vector_results = _search_vector(query_vec, candidates)  if query_vec 非零
 7. if hybrid disabled → return vector_results filtered by minScore
 8. merged = _merge_hybrid_results(vector, keyword, vectorWeight, textWeight)
 9. return [r for r in merged if score>=minScore][:maxResults]
```

- **向量路径**（`_search_vector`，`manager.py:842`）：sqlite-vec 不可用 → `_search_vector_fallback`（`:914`，纯 Python cosine 遍历所有 chunk BLOB）；否则加载候选 `chunk_map`（经 `_build_source_filter`，`:1026`，`source IN ('memory','sessions')`），`SELECT rowid, vec_distance_cosine(embedding, vec_f32(?)) ... ORDER BY distance LIMIT ?`，score = `max(0, 1 - distance/2)`（`:902`）
- **关键词路径**（`_search_keyword`，`manager.py:964`）：`build_fts_query(query)`（`internal.py:152`，取 top-10 `\w+` token 以 `OR` 拼接）→ `MATCH ?` 查 `chunks_fts` 按 FTS5 `rank` 排序 → `bm25_rank_to_score(rank)`（`internal.py:165`，`1/(1+rank)` 或 `1/(1-rank)`）
- **合并**（`_merge_hybrid_results`，`manager.py:1037`）：以向量结果建 `by_id`，再用关键词结果更新/插入；最终 `score = vectorWeight*_vector_score + textWeight*_text_score`（默认 `0.7·v + 0.3·t`），降序排序

> ⚠️ `minScore` 默认值不一致：`MemorySettings.query.minScore` 默认 `0.3`（`config.py:108`），但 `search()` 在 `opts.minScore` 缺省时硬编码 `0.7`（`manager.py:803`）。工具调用不传 minScore，因此实际始终用 0.7。这是潜在行为分歧。

## 3. 子系统二：Dreaming 睡时记忆整理

### 3.1 定位

闲时（后台）周期性扫描历史会话，调用 LLM 提取值得长期保留的内容，自动写入长期记忆文件。是会话内即时写入的**离线补充**。默认关闭，需显式开启。

> **不调用外接记忆系统**：Dreaming 全程只操作**本地文件**，不碰任何外接 provider。逐行确认 `sweeper.py`：
> - **import 无外接**（`sweeper.py:1-22`）：仅标准库 + `session_history`（读本地会话），无 `external`/`provider`/`MemoryAPI`/`MemoryProvider`/`ExternalMemoryRail`/`sync_turn`/`prefetch`/`handle_tool_call` 任何引用
> - **写操作只写本地**（`sweeper.py:521,563,590`）：`write_text` 写 `DREAMING.md`/`consolidated_*.md`/checkpoint JSON
> - **唯一外部调用是 LLM**（`sweeper.py:387-417`）：`from openjiuwen.core.foundation.llm import Model` → `model.invoke([...])`，仅用于 `_extract_via_llm` 提取事实，不是记忆系统
> - **`start_dreaming` 不传 provider**（`dreaming/__init__.py:36-66`）：参数只有 `sessions_dir`/`output_dir`/`busy_checker`，无 provider
>
> 数据流纯本地：`本地 sessions/*.jsonl` → LLM 提取 → `本地 memory/DREAMING.md` 或 `coding_memory/consolidated_*.md`。即便开了外接记忆（`engine: external`/`both`），Dreaming 也只往本地内置记忆写，**外接记忆里不会有 Dreaming 的产出**——外接只收 `ExternalMemoryRail` 的 `sync_turn`/`handle_tool_call` 内容。两者触发时机、数据源、写入目标、感知关系全独立（详见 §7 外接记忆）。要让 Dreaming 产出也进外接，需自改 sweeper 的 `promote_*` 调 provider（当前无此路径）。

> 这是一个潜在 bug/设计缺口：Dreaming code 模式的 `consolidated_*.md` 写入了但可能检索不到。`load_existing_summary`（`sweeper.py:449-475`）倒能读到（它 glob `output_dir/consolidated_*.md`，即根目录），故 Dreaming 自身去重正常；但 CodingMemoryRail 的 `coding_memory_read`/主动召回检索不到这些条目。

## 4. 子系统三：自动记忆（Auto Memory，对话后提取）

### 4.1 定位

`resolve_project_coding_memory_dir`（`coding_memory_paths.py:30-40`）：`<agent_workspace>/coding_memory/<sanitized_project_basename>/`，project 名取项目目录 basename 并把 `/`/`\` 替换为 `_`，空或 `.`/`..` 时为 `default`。

> 注意：自动记忆的 `memory_dir` 与编码记忆 Rail 的目录**统一**（都是 `coding_memory/<project>/`），因此二者共享存储。这是设计上的有意统一（`extraction_runner.py:213` 注释"unified with Auto Memory"）。

### 4.10 模式兼容性（不是只 code 模式可用）

**Auto-memory 不是只在 code 模式可用**——触发条件不含 mode 限制，但默认值与工具依赖有两个细节易引误解：

**① 触发条件不含 mode 限制（全模式可触发）**

`interface.py:1496,1933`（非流式/流式两路径）：
```python
if is_auto_memory_enabled() and is_memory_enabled(mode, config):
    _trigger_auto_memory_extraction(...)
```
`_trigger_auto_memory_extraction`（`interface.py:120-180`）**不检查 mode**，只检查 `project_dir` 非空 + 有消息。故只要两个开关开着，`agent.fast`/`agent.plan`/`code.*` 对话后都会触发。

**② 默认值让"只有 code 模式开"是误解的来源**

`is_memory_enabled(mode)` 的代码默认值（`config.py:245-247`）：code 默认 True、agent 模式默认 False。但默认 `config.yaml:935,940` **显式把 agent.fast/plan 的 `memory.enabled` 设为 true**：
```yaml
agent:
  fast:  {memory: {enabled: true, is_proactive: false}}
  plan:  {memory: {enabled: true, is_proactive: true}}
```
故**用默认 config.yaml 时，agent 模式也开着**（`enabled: true` 覆盖代码默认 False）。只有用户手动改 false 或 config 缺该项时 agent 模式才关。

→ 准确说法：**全模式可触发，触发条件是 `auto_memory_enabled` 全局开关（默认 false，`common/config.py:126`）+ 该模式 `memory.enabled`（默认 config.yaml 里 agent/code 都是 true）。故开全局开关后，全模式都触发**。

**③ 提取子代理硬依赖 coding_memory 工具/目录（关键限制）**

`extraction_runner.py:213-252`：
- `memory_dir = resolve_project_coding_memory_dir(...)` → 固定写 `<agent_workspace>/coding_memory/<project>/`（编码记忆目录，与触发模式无关）
- `_create_memory_execution_context`（`:56-146`）**自己 instantiate `CodingMemoryToolContext` + `create_coding_memory_tools`**（`:81-83,120-132`），即 `coding_memory_write/edit/read` 工具，不依赖主 agent 的 Rail
- 提取子代理用 `coding_memory_write` 写记忆文件（`prompts.py` 指示）

**④ 检索盲区（agent 模式触发的副作用）**

| 触发模式 | 写入 | 能否被检索 |
|---------|------|-----------|
| `code.*` | `coding_memory/<project>/*.md` | ✅ CodingMemoryRail 监控该目录，`coding_memory_read`/主动召回可检索 |
| `agent.fast`/`agent.plan` | 同样写 `coding_memory/<project>/*.md` | ⚠️ **agent 模式不挂 CodingMemoryRail**（见 §1 模式矩阵），写了但主 agent 检索不到——除非切 code 模式，或手动用 coding_memory 工具 |

即：**agent 模式对话后 Auto-memory 仍会提取并写入 `coding_memory/`，但这些记忆在 agent 模式下无 Rail 检索，实际"写了用不上"**。只有切到 code 模式（同 project）才会被 CodingMemoryRail 索引并召回。

## 5. 子系统四：编码记忆（Coding Memory，Code 模式专属）

### 5.1 定位

Code 模式专属的、基于文件 + 向量索引的代码上下文记忆。提供三个工具 + 一个每轮注入提示词并主动召回的 Rail。

### 5.2 三个工具

实现位于外部包 `openjiuwen.harness.tools.coding_memory`（`create_coding_memory_tools`）与 `openjiuwen.core.memory.lite.coding_memory_tool_context.CodingMemoryToolContext`。本仓库 `extraction_runner.py:81-132` 展示了构造方式。文档（`docs/zh/编码记忆.md`）定义：

| 工具 | 参数 | 行为 |
|------|------|------|
| `coding_memory_read` | `query: string` | 按关键词/语义检索匹配代码上下文，只读 |
| `coding_memory_write` | `content: string`, `section: string`（如 `architecture`/`bugfix`/`pattern`） | 写入新代码上下文/经验（YAML frontmatter + Markdown） |
| `coding_memory_edit` | `memory_id: string`, `content: string`, `section?` | 编辑已有条目，可选改分类 |

文件格式：每条 `.md` 带 frontmatter（`name`/`description`/`type`）+ 正文，共享 `MEMORY.md` 索引。

> 这三个工具**不**经 `config.yaml::modes.code.tools` 注册（配置注释明确：`coding_memory_read/write/edit 由 CodingMemoryRail 在 subagent 内部注册，不在此配置`），而是由 `CodingMemoryRail.init()` 挂载到 agent 的 ability_manager。

### 5.3 CodingMemoryRail

外部包类（`openjiuwen.harness.rails.CodingMemoryRail`），行为由本仓库 `tests/unit_tests/agentserver/memory/test_coding_memory_rail.py:154-378` 的忠实 mock 反映：

- `AgentRail`（`priority = 80`），持有 `coding_memory_dir`、`embedding_config`、惰性 `MemoryIndexManager`
- 常量 `MAX_RECALL_RESULTS = 5`、`MAX_RECALL_TOTAL_BYTES = 10240`
- **构造**（本仓库 `interface_code.py:279-318` `create_coding_memory_rail`）：`CodingMemoryRail(coding_memory_dir=<project 级目录>, embedding_config=EmbeddingConfig(...), language="en")`。embed 配置不全则强制 `embed_api_key=None`，注册"memory fallback provider"（`:296-302`）
- `init(agent)`：取 `agent.system_prompt_builder`，注册自有工具
- `before_invoke(ctx)`：惰性初始化 `MemoryIndexManager`（键 `agent_id:coding_memory_dir`，缓存）；**只读调用（cron/heartbeat）跳过预取**；否则取最后一条 user 消息作 `query`，起后台 `asyncio.Task` 跑 `_auto_recall(query)`（与模型思考并发的主动召回）

- `before_model_call(ctx)` — **系统提示词注入**：`remove_section("memory")` 后重建 `PromptSection(name="memory", priority=85)`；基础内容描述持久记忆位置与可用工具；只读模式注入"只读/不写"变体；有预取结果则追加 `## Loaded relevant memories` + 召回片段；否则追加 `## Current memory index`（`MEMORY.md` 前 200 行）

### 5.4 存储布局

路径解析在 `jiuwenswarm/common/coding_memory_paths.py`：

- `resolve_coding_memory_project_name(project_dir)`（`:14-27`）：项目目录 basename，`/`/`\` → `_`
- `resolve_project_coding_memory_dir(agent_workspace_dir, project_dir)`（`:30-40`）→ `<agent_workspace>/coding_memory/<project_name>`

典型路径（编码记忆 Rail 监控范围）：
```
<agent_workspace>/coding_memory/<project_basename>/   ← CodingMemoryRail manager workspace（非递归扫 *.md）
├── MEMORY.md                    # 索引（前 200 行作回退注入）
├── <semantic>.md                # coding_memory_write / Auto-memory 写入的条目
└── memory.db                    # MemoryIndexManager 的向量+FTS 索引

<agent_workspace>/coding_memory/                        ← Dreaming code 模式 output_dir（根）
└── consolidated_<hash>.md       # Dreaming(code) 产出；⚠️ 不在上方 <project>/ 内，不被编码记忆索引（§3.6）
```

### 5.6 与 Dreaming（code 模式）与 MemoryIndexManager 的关系

- Dreaming code 模式 → `consolidated_{hash}.md`：`Sweeper.promote_code`（`sweeper.py:546-564`）写提取知识到 sweeper 的 `_output_dir`；该目录即 `<agent_workspace>/coding_memory/`（**根**，`interface_deep.py:7392-7394`，`_dreaming_mode="code"` 由 `interface_code.py:453` 设定）。Dreaming 扫描时按 `metadata.json::mode` 前缀 `code` 过滤（`_match_session_mode`，`:287-298`）。**注意路径不匹配**：该根目录与编码记忆 Rail 监控的 `coding_memory/<project>/` 子目录不重合，Dreaming code 产出不被编码记忆索引——详见 §3.6

### 7.2 `memory.engine` 配置与解析

> 关键：`build_external_memory_rail` 自身**不检查 engine 门控**，只检查 `provider`。engine 门控是**调用方**职责（经 `is_external_memory_enabled()`）。故 `engine=builtin` + `provider=mem0` 直接调 builder 仍会构造 Mem0 rail，但 DeepAdapter 路径因 `is_external_memory_enabled` 返 false 不会调它（测试 `test_engine_builtin_still_builds_caller_must_gate` 明确文档化此约定）。

### 7.4 engine 如何决定 builtin 和/或 external 运行

两个 Rail 由 DeepAdapter 的两个方法独立门控：

**Builtin（MemoryRail / MemoryIndexManager）** — `_handle_memory_rail_by_config(mode)`（`interface_deep.py:6413-6437`）：
- 门控 `get_memory_mode(config) == "local"`（`:6415`，仅 local 存储模式挂内置 rail，cloud 跳过）
- `builtin_on = is_builtin_memory_allowed(config) AND is_memory_enabled(mode, config)`（`:6417`）——三条件：`engine ∈ {builtin, both}` AND `memory.mode=local` AND `modes.<mode>.memory.enabled=true`
- 开启且 proactive 标志自上次注册变化则注销重建（`:6420-6428`）
- 经 `_build_memory_rail(mode)`（`:2852-2880`）构造 `MemoryRail(embedding_config=EmbeddingConfig(...), is_proactive=...)`；`is_proactive` 由 `is_proactive_memory(mode, config)`（`config.py:254-264`，默认 False）决定

**External（ExternalMemoryRail）** — `_handle_external_memory_rail_by_config()`（`interface_deep.py:6449-6495`）：
- 门控 `is_external_memory_enabled(config)`（`:6463`）= `engine ∈ {external, both}` AND `provider != ""`；**无模式依赖、无 `memory.mode` 检查**
- `self._external_memory_rail_registered` 去重（`:6464-6472`，因 plan 和 fast 模式都调）
- 经 `_build_external_memory_rail()`（`:6439-6447`）调 `build_external_memory_rail(config=get_config(), workspace_dir=self._workspace_dir)`
- 禁用时先 `provider.on_session_end()` 再 `unregister_rail`（`:6477-6495`，因 unregister→uninit 同步会死锁）
- **刻意不进** `_get_current_agent_rails()`，故配置热重载不拆除它（保 prefetch 缓存 + 断路器状态，docstring `:6450-6457`）

### 7.5 触发时机 / 生命周期

两方法由 DeepAdapter 的**模式切换 Rail 生命周期**调用：
- `_update_plan_mode_rails`（`:3839`）→ `_handle_memory_rail_by_config("plan")`（`:3853`）+ `_handle_external_memory_rail_by_config()`（`:3855`）
- `_update_agent_mode_rails(mode)`（`:3921`）→ `_handle_memory_rail_by_config("fast")`（`:3944`）+ `_handle_external_memory_rail_by_config()`（`:3946`）
- `_update_rails_for_mode(mode)`（`:3832`）分派到 plan/agent 更新器

**注意**：这些在**模式切换时**运行（plan ↔ fast/agent），非每轮。External rail 不每轮重建（与 ProjectMemoryRail 不同），其检索生命周期由 provider 自管。

**Code 模式**：`JiuWenSwarmCodeAdapter` 继承这些 handler 但覆写 `_update_rails_for_mode`（`interface_code.py:1019`），其 `_build_agent_rails`（`:539`）固定 Rail 列表不含 `_external_memory_rail`，且 code 的 `_update_rails_for_mode`（`:1019-1074`）不调 `_handle_external_memory_rail_by_config`。`MemoryRail`（内置）在 code 模式也不支持（`interface_code.py:597-601` 日志提示改用 `CodingMemoryRail`）。故 external memory 实际为 **deep/agent plan+fast 模式**装配。

## 11. 关键发现与风险

1. **`memory_tools.py` 的全局管理器 API 是死代码**：`set_global_memory_manager`/`init_memory_manager_async` 全仓零调用。live agent 用 openjiuwen SDK 的记忆工具（`interface_deep.py:4312-4319`），其管理器由 Rail/SDK 持有。依赖 `memory_tools.py` 工具的消费者需从 SDK bootstrap 显式调 setter。

2. **`MemoryRail` 冷启动不挂载**：仅在每轮 `process_message*` 跑 `_update_runtime_config` 时按模式注册。故 `create_instance` 后首轮才出现。

3. **Dreaming 以非 await 的 `asyncio.create_task` 启动**（`interface.py:632, 668`），`create_instance`/`reload_agent_config` 在 dreaming 完全起来前就返回；`try_stop_dreaming` 是唯一 await 的 dreaming 调用（`:663`）；`cleanup` 不停 dreaming，依赖进程/loop teardown。

4. **自动记忆与云记忆 after-chat 相互独立**：二者都对话后跑，但 auto-memory 是本地子代理路径（`_execute_auto_memory_extraction`），云 after-chat 是扩展 hook 路径（`MEMORY_AFTER_CHAT`）；`memory_mode=="cloud"` 且 auto-memory 开启时两者都可触发，目标不同存储。

5. **auto-memory 的互斥是"主代理本轮是否已写记忆"**（`extraction_runner.py:203-207`），防止内联 coding-memory 工具与后台提取子代理重复写。

6. **`minScore` 默认值分歧**：`MemorySettings.query.minScore` 默认 `0.3`（`config.py:108`），但 `search()` 硬编码 `0.7`（`manager.py:803`），工具调用不传 minScore 故实际恒用 0.7。潜在行为分歧。

7. **openjiuwen 未安装**：`DreamingOrchestrator`/`MemoryRail`/`CodingMemoryRail`/`ExternalMemoryRail`/`DeepAgent`/`Model` 均外部。任何对 orchestrator 循环契约（interval/busy 语义、checkpoint 名）的改动需上游协调；本仓库仅提供 `Sweeper` + 接线。

8. **两类"记忆"在提示词侧并存且独立**：(a) `MemoryIndexManager`（向量+FTS 索引）；(b) `ProjectMemoryRail`（从 `JIUWENSWARM.md` 重建 `project_memory` 段）。索引不喂 Rail，Rail 不喂索引。

9. **watchdog 武装延迟**（`manager.py:402`，1.0s `call_later`）仅在 `_setup_file_watcher` 后首秒抑制事件；慢初始 sync 期间的外部批量重写可能经 2s 去抖正确排队，但该窗口内批量外部重写可能双触发。

10. **Dreaming LLM 失败处理**：`scanned_sessions` 仅成功时更新（`sweeper.py:165-175`），transient LLM 失败会下次重试——好；但 `_extract_via_llm` 把所有异常吞成 `return []`（`:431-433`），空列表也算"成功"（`:159`），故因解析错误而非真无知识导致的空结果也会被标记 scanned 不再重试。

11. **Dreaming code 模式路径不匹配（潜在 bug）**：Dreaming code 模式 `output_dir = <agent_workspace>/coding_memory/`（根，`interface_deep.py:7392-7394`），写 `consolidated_*.md` 到根；而 CodingMemoryRail 监控 `<agent_workspace>/coding_memory/<project>/`（子目录，`coding_memory_paths.py:43-51`），且 openjiuwen `list_memory_files`（`core/memory/lite/internal.py:33`）用 `os.listdir` 非递归。→ Dreaming code 产出**不被编码记忆索引**，`coding_memory_read`/主动召回检索不到（Dreaming 自身 `load_existing_summary` 仍能读，去重正常）。详见 §3.6。修复方向：让 Dreaming code 的 `output_dir` 带 project 上下文，或扩 CodingMemoryRail 监控到 `coding_memory/` 根。

12. **群聊守卫**：`write_memory`/`edit_memory` 在 `is_group_chat_mode()` 为 True 时硬阻断（`memory_tools.py:307, 368`），由 `_GROUP_CHAT_MODE` context var（`:24`）控制——索引层唯一的群聊语义接触点。

13. **`is_proactive_memory`**（`config.py:254`）门控代理是否每次响应前自动搜索；切换它强制 `MemoryRail` 注销/重注册（`interface_deep.py:6420-6428`）但**不动** `MemoryIndexManager`——索引在 memory 启用时始终构建，proactive 只改提示词注入节奏。

14. **经验记忆（task_memory）文档描述的是意图非现状**："enabled: true 后 Agent 获得三工具"是愿景——注册胶水（`_TOOL_BUILD_NAMES` 条目、`modes.code.tools` 项、swarm provider、`ability_manager.add()` 调用）从未写。本地持久化（`task-data.json` + `persisted_only` 回退）确实在工具体内实现，但工具从不被注册，故运行时不可达。

15. **external memory 仅 deep/agent plan+fast 模式装配**：Code 适配器覆写的 `_update_rails_for_mode` 不调 `_handle_external_memory_rail_by_config`，且 code 固定 Rail 列表不含 external；`MemoryRail`（内置）在 code 也不支持。故 `engine=both` 在 code 模式实际只有 `CodingMemoryRail` 起作用。
